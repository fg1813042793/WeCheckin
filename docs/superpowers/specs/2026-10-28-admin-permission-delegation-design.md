# Admin 权限委派上限设计

## 目标

子管理员只能查看、创建、修改和分配不超过自身有效权限的数据，任何隐藏字段或直接 HTTP 请求都不能突破该限制。保留角色名为“超级管理员”的账号拥有完整委派能力。

## 委派上限

新增 Admin 委派上限解析器，基于当前用户的全部启用角色、用户直接允许/拒绝授权及数据范围计算：

- 后台菜单权限；
- 后台 API 权限；
- Client 菜单与 API 权限；
- 钉钉 H5 菜单、按钮与 API 权限；
- 基础数据范围和额外部门、额外用户范围；
- 是否为保留超级管理员。

拒绝授权优先于允许授权。保留超级管理员不受委派上限限制。

## 权限树

`/api/v2/admin/permissions/tree`、`/api/v2/admin/permissions` 和 `/api/v2/admin/roles/application-permissions` 按当前管理员有效权限过滤。树结构保留命中叶子的父级目录和 API 分类，但父级目录本身不会因此变成可授予权限。

权限目录的新增、修改和删除只允许保留超级管理员执行，防止子管理员通过修改权限编码间接获得敏感接口权限。

## 角色管理

角色列表只返回当前管理员数据范围内且可委派的角色。角色新增、编辑、删除和批量删除都在后端执行以下校验：

- 目标角色属于当前管理员可管理的数据范围；
- 角色的后台、Client、钉钉 H5 权限均为当前管理员有效权限的子集；
- 保留超级管理员角色只能由保留超级管理员管理；
- `data:all` 只能由拥有全部数据权限的管理员授予；
- `data:dept` 只能由本部门及下级部门或全部数据权限管理员授予；
- `data:self` 可由任何有效管理员授予；
- 自定义部门必须是当前管理员可见部门的子集。

## 用户管理

新增用户和编辑用户统一传递当前管理员 ID，并校验：

- 用户所属部门和直属上级在当前管理员可见范围内；
- 分配的每个角色均可由当前管理员委派；
- 用户直接允许和拒绝的应用权限均在当前管理员有效应用权限内；
- 额外部门和额外用户均在当前管理员可见范围内；
- 保留超级管理员角色不能由子管理员分配。

## 前端行为

前端继续使用现有接口和树组件。后端返回过滤后的树、角色列表和可授予数据范围元数据，因此角色页与用户页只展示可委派选项。保存失败时沿用统一请求错误提示，不依赖前端隐藏实现安全控制。

## 验证

- 单元测试覆盖委派上限、树过滤、角色权限子集、角色分配、数据范围和超级管理员旁路；
- Handler/Service 结构测试覆盖当前管理员 ID 的传递；
- Admin 静态检查和构建验证现有页面契约；
- Backend 定向测试和全量测试区分本次回归与仓库既有失败。
