# H5App 站内信入口设计

## 目标

在 H5App 应用壳右上角增加站内信图标按钮，位置固定在“切换菜单布局”按钮左侧。普通用户可以查看属于自己的站内通知、查看未读数量并更新已读状态；流程通知可以继续进入对应流程实例详情。

本次复用现有 `notify` 表和流程 `in_app` 投递逻辑，不改流程定义格式，不新增通知存储表。

## 交互设计

- 站内信按钮使用消息或铃铛图标，保持与现有布局切换、刷新按钮相同的方形工具按钮样式。
- 有未读通知时，在图标右上角显示数量徽标；零条时隐藏，超过 99 条显示 `99+`。
- PC 端点击按钮，从右侧打开约 420px 宽的通知抽屉。
- 手机端点击按钮，使用覆盖应用内容区的全屏通知面板，避免窄屏抽屉压缩内容。
- 面板顶部显示“站内信”、未读数量和“全部已读”操作。
- 通知列表按创建时间倒序展示标题、内容摘要、时间和未读状态。
- 打开面板时刷新列表和未读数量；支持加载、空数据和失败状态。
- 点击未读通知后先标记已读。流程通知根据 `sourceType=workflow_instance` 和 `sourceId` 打开对应流程实例详情 Tab；其他通知保留在当前面板中查看完整内容。
- 关闭面板后不改变当前业务页面和菜单布局。

## 后端接口

在 `/api/v2/dingtalk/h5` 下新增当前用户站内信接口：

- `GET /notifications?page=&pageSize=`：分页查询当前登录用户的通知。
- `GET /notifications/unread-count`：查询当前登录用户未读数量。
- `PATCH /notifications/:id/read`：将当前用户拥有的一条通知标记为已读。
- `PATCH /notifications/read-all`：将当前用户的全部未读通知标记为已读。

接口从钉钉 H5 登录态解析本地用户 ID，不接受客户端传入 `userId`。列表和更新都必须使用 `notify_user_id = 当前用户ID` 约束；不向普通用户返回 `notify_user_id=''` 的管理员广播通知。

响应使用明确 DTO，通知记录包含 `id`、`title`、`content`、`type`、`sourceType`、`sourceId`、`isRead` 和 `addTime`。不存在或不属于当前用户的通知统一返回未找到，避免泄露其他用户数据。

## 前端结构

- `src/api/notifications.ts`：站内信请求和响应类型。
- `src/components/app-shell/app-shell.vue`：入口按钮、未读徽标和面板开关。
- 独立站内信面板组件负责列表、分页、已读操作和通知点击，不把业务请求堆入应用壳。
- 流程实例跳转复用 `appContent` 已有动态 Tab 能力，不新增 uni-app 页面。
- 用户可见文案同步维护中英文语言包。

## 权限与兼容性

- 站内信属于所有已登录用户的基础能力，入口不依赖业务菜单是否授权。
- 后端仍要求有效的钉钉 H5 登录态，并对每次查询和更新执行用户归属校验。
- 现有 Admin 问卷通知接口和流程通知投递记录页面保持不变。
- 现有 `notify` 数据结构可以满足本次需求，不需要数据库结构迁移。

## 验证

- 后端测试覆盖用户隔离、分页、未读数量、单条已读、全部已读和越权访问。
- H5App 静态检查覆盖 API 类型、组件事件和语言包。
- 运行 `pnpm lint`、`pnpm type-check`、`pnpm check:dingtalk-module`、`pnpm check:workflow-module` 和 `pnpm build:h5`。
- 在 PC 和手机宽度下验证按钮位置、徽标、面板尺寸、滚动、空状态、已读更新和流程详情 Tab 跳转。
