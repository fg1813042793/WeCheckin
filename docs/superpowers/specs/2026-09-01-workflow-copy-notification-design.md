# 通用工作流抄送与通知设计

## 1. 目标与边界

在独立的通用 Go 工作流模块中补齐可复用的抄送和通知闭环，使流程定义能够表达“谁可以只读查看”和“向谁发送什么消息”，并通过事务性 Outbox 保证流程状态与待发送消息一致。

本期包含：

- 抄送节点 `cc`：记录抄送参与人、授予流程只读访问权并按配置发送通知。
- 通知节点 `notify`：只发送通知，不创建任务、不授予流程访问权。
- 审批节点 `approval` 和办理节点 `handle` 的任务到达通知。
- 站内通知和钉钉 OA 工作通知两种渠道。
- 事务性 Outbox、投递状态查询、失败重试和管理端人工重试。
- 管理端流程设计器的节点配置、校验和实例投递记录展示。

本期不包含：

- 修改或迁移现有绩效业务流程及其通知代码。
- `h5app` 工作流中心、待办详情、抄送列表和深链页面。
- 邮件、短信、Webhook、群机器人等其他渠道。
- 任意表达式、脚本或直接读取全部表单数据的消息模板。
- 全局通用任务调度平台。本期采用提交后立即投递和管理端显式重试；Outbox 保留后续调度器接入点。

## 2. 术语与行为语义

### 2.1 抄送节点 `cc`

抄送节点复用现有人员解析器。令牌到达节点后，在同一事务内完成以下动作：

1. 解析并去重抄送接收人。
2. 为每个接收人写入流程参与人记录，角色为 `cc`。
3. 写入 `node_cc` 历史事件。
4. 按节点通知配置为每个接收人和渠道写入 Outbox。
5. 令牌立即继续，不创建人工任务。

抄送接收人可以只读查看流程实例、表单当前值和流程历史，但不能处理任务、撤回、取消或修改表单。抄送权限由参与人记录决定，不能依赖通知是否成功送达。

### 2.2 通知节点 `notify`

通知节点同样复用人员解析器。令牌到达后为接收人和渠道写入 Outbox，然后立即继续。通知节点不创建任务、不写入参与人表，也不因此赋予实例访问权。

通知节点适用于向流程外的人员发送进度提醒。由于接收人可能没有实例查看权限，本期通知内容不附带工作流详情深链，只使用钉钉应用首页地址。

### 2.3 任务到达通知

审批和办理节点成功创建人工任务时，可以为任务处理人生成 `task_arrived` 通知。通知与任务在同一事务内落库；并行任务或会签任务按实际生成的任务逐人通知。

任务因重试、事务回放或重复推进而被再次检查时，Outbox 唯一键保证同一任务、接收人和渠道只生成一次通知。

## 3. 流程定义契约

节点新增可选的 `notification` 配置：

```json
{
  "notification": {
    "enabled": true,
    "channels": ["in_app", "dingtalk_oa"],
    "title": "{{workflowName}}",
    "content": "{{starterName}} 发起的流程已到达 {{nodeName}}"
  }
}
```

字段约束：

- `enabled`：是否生成通知；未配置或为 `false` 时不生成 Outbox。
- `channels`：非空且去重，只允许 `in_app`、`dingtalk_oa`。
- `title`：模板原文 1 至 256 个字符，渲染后按字符安全截断为 64 个字符。
- `content`：模板原文 1 至 2000 个字符，渲染后按字符安全截断为 1000 个字符。

首版模板只允许以下白名单占位符：

- `{{workflowName}}`：流程定义名称。
- `{{nodeName}}`：当前节点名称。
- `{{starterName}}`：发起人显示名称。
- `{{instanceId}}`：流程实例 ID。
- `{{taskId}}`：任务 ID；非任务通知渲染为空字符串。

未知占位符在定义校验时直接报错。模板不支持条件、循环、函数、变量路径或表单字段插值，避免流程设计者无意泄露敏感表单数据。

`cc` 和 `notify` 都复用节点现有的 `assignee` 人员来源配置。`notify` 必须同时配置有效接收人和启用的通知配置；`cc` 必须配置有效接收人，通知配置可以关闭；`approval` 和 `handle` 仅在启用任务到达通知时校验通知模板和渠道。

管理端新增节点时采用以下默认值：

- 新增 `cc`：默认启用通知，渠道为站内和钉钉 OA，标题为 `{{workflowName}}`，内容为 `{{starterName}} 发起的流程已抄送给你`。
- 新增 `notify`：默认启用通知，渠道为站内和钉钉 OA，标题为 `{{workflowName}}`，内容为 `流程已到达 {{nodeName}}`。
- 新增 `approval`、`handle`：默认启用任务到达通知，渠道为站内和钉钉 OA，标题为 `{{workflowName}}`，内容为 `你有一项待处理任务：{{nodeName}}`。

兼容规则：旧定义中不存在 `notification` 时视为禁用通知。旧 `cc` 节点后续执行时仍会写入抄送参与人和历史记录，但不自动对外发送消息；已完成的历史节点不回填参与人或通知。

BPMN 导出继续以 `serviceTask` 表示 `cc`，新增 `serviceTask` 表示 `notify`，并通过扩展属性保留人员来源和通知配置。Go 引擎仍以发布版本 JSON 为唯一运行依据，BPMN 不参与运行时反向解析。

## 4. 分层设计

### 4.1 领域层

工作流领域层只生成与渠道无关的通知意图，不依赖钉钉、绩效或内容模块。通知意图至少包含：

- 事件类型：`node_cc`、`node_notify` 或 `task_arrived`。
- 实例、节点和可选任务标识。
- 接收人的本地用户 ID。
- 通知配置和模板上下文标识。

领域状态同时携带新增的抄送参与人和通知意图，由应用层在保存流程状态时一并持久化。

### 4.2 应用层

应用服务在现有流程事务中完成：

1. 保存实例、令牌、任务、变量和历史。
2. 幂等写入抄送参与人。
3. 将通知意图展开为“接收人 × 渠道”的 Outbox 记录。
4. 提交事务。

事务提交后，应用服务对本次产生的 Outbox 执行一次即时投递。外部渠道失败不能回滚已经提交的流程；Outbox 或参与人写入失败必须回滚整个流程事务，防止流程已推进但通知意图永久丢失。

### 4.3 渠道适配器

投递器通过统一接口调用渠道适配器：

```go
type NotificationChannel interface {
    Name() string
    Deliver(ctx context.Context, message NotificationMessage) error
}
```

- `in_app` 适配器直接写入现有 `notify` 表，使用 `type=workflow`、`source_type=workflow_instance`、`source_id=<instanceId>`。
- `dingtalk_oa` 适配器复用现有 `DingTalkWorkNotificationClient`，但不能依赖绩效通知包。
- 工作流模块通过接口依赖适配器，钉钉实现放在基础设施层，避免 workflow 领域层反向依赖 `dingtalkh5/performance`。

钉钉通知 URL 本期使用对应企业配置的 `AppURL`。工作流 H5 深链在第二期实现后再扩展 URL 生成器，不改变 Outbox 或渠道接口。

站内通知的插入和 Outbox `sent` 状态更新使用同一个数据库事务，进程中断时两者同时提交或同时回滚。钉钉属于外部系统，无法跨系统实现严格的恰好一次：正常重试由 Outbox 幂等控制，但在钉钉已经接收、客户端却没有收到成功响应的极端情况下可能产生重复 OA 消息，系统按至少一次投递语义处理并保留投递日志。

## 5. 数据模型

### 5.1 流程参与人

新增 `workflow_instance_participants`：

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `instance_id` | 流程实例 ID |
| `user_id` | 本地用户 ID |
| `role` | 首版固定为 `cc` |
| `node_id` | 产生参与关系的节点 ID |
| `add_time` | 创建时间 |

使用 `(instance_id, user_id, role, node_id)` 唯一约束保证重复推进幂等。同一用户被多个节点抄送时允许保留多条来源记录，访问校验只需存在任一有效记录。

### 5.2 通知 Outbox

新增 `workflow_notification_outbox`：

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `instance_id` | 流程实例 ID |
| `node_id` | 节点 ID |
| `task_id` | 可空任务 ID |
| `recipient_user_id` | 本地接收人 ID |
| `kind` | `node_cc`、`node_notify`、`task_arrived` |
| `channel` | `in_app`、`dingtalk_oa` |
| `status` | `pending`、`sending`、`sent`、`failed`、`dead` |
| `dedupe_key` | 全局唯一幂等键 |
| `payload_json` | 已渲染标题、正文和来源信息 |
| `corp_id` | 首次解析后固定的钉钉企业 ID，可空 |
| `provider_message_id` | 渠道返回的消息标识，可空 |
| `attempts` | 已尝试次数 |
| `next_retry_at` | 下次允许重试时间 |
| `last_error` | 最近一次失败摘要 |
| `sent_at` | 成功时间 |
| `add_time`、`edit_time` | 创建和更新时间 |

幂等键格式为：

```text
<instanceId>:<kind>:<nodeId>:<taskId>:<recipientUserId>:<channel>
```

空任务 ID 使用固定占位值 `-`。Outbox 只保存投递所需快照，重试时不重新读取当前流程定义模板，避免定义或显示名称变化导致同一通知内容漂移。

## 6. 投递、重试与企业解析

投递器用条件更新把 `pending` 或到期的 `failed` 记录抢占为 `sending`，成功后更新为 `sent`。失败时记录简化错误信息、递增 `attempts`，并按 `1 分钟、5 分钟、30 分钟、2 小时、12 小时` 设置 `next_retry_at`；第五次失败后标记为 `dead`。

本期投递入口有两个：

- 流程事务提交后，立即投递本次新建的 Outbox。
- 管理端显式执行“投递到期通知”或对单条记录执行“重试”。

这两个入口使用同一抢占和幂等逻辑。提交后即时投递按企业、渠道和相同消息内容批量合并接收人，并设置调用超时，避免接收人数增加时逐人阻塞流程请求。服务进程在发送完成前退出时，`sending` 超过 10 分钟视为失效锁，可被下一次投递重新抢占。后续接入统一调度器时，只需周期调用“投递到期通知”应用服务。

钉钉企业和用户绑定按以下规则解析：

1. 按企业 ID 排序发起人的有效企业绑定，选择其中第一个同时存在接收人有效绑定且已启用通知的企业。
2. 若没有共同企业，选择接收人有效绑定中企业 ID 最小且通知已启用的企业。
3. 首次解析成功后把 `corp_id` 固定到 Outbox，后续重试使用同一企业。
4. 无有效绑定、企业通知关闭或配置不完整时记为失败，保留明确错误，管理员修复配置后可以重试。

站内通知与钉钉通知分别独立记录状态；其中一个渠道失败不影响另一个渠道成功。

## 7. 权限与查询

流程实例详情的访问判定扩展为满足任一条件即可：

- 当前用户是发起人。
- 当前用户拥有该实例的任务。
- 当前用户存在 `cc` 参与人记录。

抄送参与人只有只读权限。任务处理、撤回、取消等写操作继续使用原有身份和权限判断，不能因为存在参与人记录而放宽。

客户端实例列表增加 `scope` 查询参数：

- `started`：我发起的，保持现有默认行为。
- `handled`：我拥有或处理过任务的。
- `copied`：抄送给我的。

本期只补齐后端查询能力，不在 `h5app` 增加工作流页面。

## 8. 管理端设计

流程设计器将现有“抄送/通知”拆分为两个独立节点：

- `抄送`：配置接收人、是否发送通知、渠道、标题和正文。
- `通知`：配置接收人、渠道、标题和正文；通知必须启用。

审批和办理节点增加“任务到达通知”开关及同一套渠道和模板配置。节点摘要显示通知开关和渠道，不在画布上展示完整正文。

流程实例详情新增“通知投递”区域，展示接收人、事件、渠道、状态、尝试次数、最近错误和发送时间。管理员可以重试单条 `failed`、`dead` 记录，也可以触发一次到期记录投递。现有把 `node_cc` 显示为“抄送通知已发送”的文案改为“已记录抄送”，实际发送结果以 Outbox 状态为准。

## 9. HTTP 接口

新增管理接口：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/v2/admin/workflow-notifications` | 按实例、状态和渠道查询 Outbox |
| `POST` | `/api/v2/admin/workflow-notifications/:id/retry` | 重置并立即重试一条通知 |
| `POST` | `/api/v2/admin/workflow-notifications/dispatch-due` | 投递到期的待发送和失败通知 |

客户端继续使用现有流程实例列表和详情接口，只增加 `scope` 过滤能力。管理接口新增 `workflow:notification:list` 和 `workflow:notification:retry` 权限码并纳入现有权限中间件；查询接口使用前者，单条重试和到期投递使用后者。迁移只注册权限，不自动扩大现有角色授权。

## 10. 错误处理与安全

- 人员解析失败、通知定义无效、参与人或 Outbox 持久化失败：流程事务失败并回滚。
- 站内或钉钉渠道发送失败：流程不回滚，Outbox 记录失败并等待重试。
- 通知正文和错误信息返回管理端前执行长度限制；日志不记录钉钉密钥、Token 或完整敏感响应。
- Outbox 查询和重试仅允许具备工作流管理权限的管理员。
- 普通用户查询实例时始终从认证上下文获取用户 ID，不接受请求参数冒充抄送人。
- 模板首版不读取任意流程变量或表单值，避免敏感数据通过通知渠道扩散。

## 11. 测试与验收

后端测试至少覆盖：

- `cc` 节点写入参与人、历史和 Outbox，并继续流程。
- `notify` 节点写入 Outbox，但不写参与人、不授予访问权。
- 审批和办理任务创建时生成到达通知。
- 同一事务失败时流程状态、参与人和 Outbox 一起回滚。
- 幂等键阻止重复通知，两个渠道状态相互独立。
- 发送成功、退避重试、第五次失败进入 `dead`、失效 `sending` 重新抢占。
- 站内通知与 Outbox 状态同事务提交，重试不产生重复站内消息。
- 钉钉企业解析、无绑定、通知关闭和发送失败路径。
- 抄送人可以查看详情但不能处理任务，`scope=copied` 只返回抄送实例。
- 管理端查询、单条重试和到期投递接口的认证、权限与参数校验。

管理端测试至少覆盖：

- `cc` 与 `notify` 在组件面板、流程树、配置抽屉和 BPMN 导出中的独立语义。
- 三类通知配置的默认值、校验、保存和旧定义回显。
- 实例详情展示真实投递状态并可触发重试。
- 历史中的 `node_cc` 不再宣称消息已经发送。

最终验证运行工作流相关 Go 定向测试、数据库迁移测试、管理端工作流静态回归检查和完整管理端构建。钉钉真实账号和 H5 页面由用户在后续阶段做手工联调。
