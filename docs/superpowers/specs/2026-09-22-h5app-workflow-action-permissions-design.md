# H5App OA 流程操作权限细分设计

## 目标

将钉钉 H5 通用 OA 流程中当前共用“OA 流程处理接口”的四类动作拆分为独立权限：通过审批、驳回流程、退回流程和提交办理。发起人撤回申请继续使用现有“OA 流程撤回接口”，不改变语义。

权限细分必须同时覆盖前端按钮显示和后端接口鉴权，不能只隐藏按钮；直接调用统一任务完成接口时，后端仍需根据请求中的 `action` 校验对应权限。

本次只修改 `h5app/` 与 `/api/v2/dingtalk/h5` 权限链路，不修改 `frontend/` 客户端权限，也不修改绩效考评流程权限。

## 权限模型

新增四个按钮权限：

| 权限键 | 名称 | 作用 |
| --- | --- | --- |
| `dingtalk_h5:button:workflow:approve` | 通过审批 | 显示审批节点的确认通过按钮 |
| `dingtalk_h5:button:workflow:reject` | 驳回流程 | 显示审批节点的驳回按钮 |
| `dingtalk_h5:button:workflow:return` | 退回流程 | 显示符合退回条件的退回按钮 |
| `dingtalk_h5:button:workflow:submit` | 提交办理 | 显示办理节点的提交办理按钮 |

新增四个 API 权限：

| 权限键 | 名称 | action |
| --- | --- | --- |
| `dingtalk_h5:api:workflow:approve` | OA 流程通过接口 | `approve` |
| `dingtalk_h5:api:workflow:reject` | OA 流程驳回接口 | `reject` |
| `dingtalk_h5:api:workflow:return` | OA 流程退回接口 | `return` |
| `dingtalk_h5:api:workflow:submit` | OA 流程提交办理接口 | `submit` |

四个动作继续调用同一个业务接口：

```text
POST /api/v2/dingtalk/h5/workflows/tasks/:id/complete
```

现有 `dingtalk_h5:api:workflow:withdraw` 继续只控制发起人撤回实例。它不参与任务通过、驳回、退回和提交办理。

## 后端鉴权

`DingTalkH5Perm` 对任务完成接口增加 action 感知：

1. 识别 `POST /api/v2/dingtalk/h5/workflows/tasks/:id/complete`。
2. 从 JSON 请求体读取 `action`，映射到四个新 API 权限之一。
3. 使用现有用户、角色、直接拒绝和权限快照规则校验映射后的权限键。
4. 权限不足时返回现有“无权限访问”，不得进入工作流应用服务。
5. 请求体缺失、格式错误或 action 不在允许枚举内时返回参数错误，不将其降级到任一有效动作权限。

请求体由 Hertz 保存在内存字节数组中，权限中间件读取后不修改请求体，业务 Handler 仍按现有方式解码并执行。

`DingTalkH5RouteDeclarations` 不再为任务完成接口声明单一静态权限。四个新 API 权限仍保留相同的资源路径用于后台展示，但静态路由声明生成时排除这四项，避免相同 method/path 的声明顺序决定鉴权结果。

工作流领域层和应用层保持不变，仍负责校验任务归属、节点类型、动作合法性、驳回原因、退回目标和流程状态。权限中间件只决定当前用户是否允许请求该动作。

## H5App 按钮规则

保留现有 `activeTask`、当前任务处理人和节点类型判断，在此基础上分别计算：

- `canApprove`：当前用户有待处理审批任务，同时拥有通过按钮权限和通过 API 权限。
- `canReject`：当前用户有待处理审批任务，同时拥有驳回按钮权限和驳回 API 权限。
- `canReturn`：满足现有可退回路径、非并行限制，同时拥有退回按钮权限和退回 API 权限。
- `canSubmit`：当前用户有待处理办理任务，同时拥有提交办理按钮权限和提交 API 权限。

页面允许只展示部分动作。例如用户只有驳回权限时，可以查看当前待办并执行驳回，但不会看到通过或退回按钮。

前端按钮权限只改善交互，后端 action 权限校验是最终安全边界。

## 历史权限迁移

新增版本化 SQL，写入八个新权限，并从已有 `dingtalk_h5:api:workflow:handle` 有效授权复制到四个按钮权限和四个 API 权限：

- 复制主体类型和主体 ID。
- 保留 `allow`、`deny` 效果和有效状态，避免直接拒绝规则丢失。
- 保留作用域值；新权限不额外解释作用域，但迁移不得擅自丢弃历史数据。
- 使用 `ON DUPLICATE KEY UPDATE` 保证迁移可重复执行。

完成复制后，将旧 `dingtalk_h5:api:workflow:handle` 权限标记为停用，并从代码目录声明中移除。历史授权记录保留用于审计，但不再参与运行时鉴权或后台新授权。

因此升级后已有角色默认继续拥有原先全部处理能力；管理员可以随后在角色权限中单独取消通过、驳回、退回或提交办理。

## 后台权限配置

现有角色权限页面会通过统一权限目录自动展示新增按钮和 API 权限，不增加独立配置页面。

建议关系保持直接：

- “通过审批”按钮对应“OA 流程通过接口”。
- “驳回流程”按钮对应“OA 流程驳回接口”。
- “退回流程”按钮对应“OA 流程退回接口”。
- “提交办理”按钮对应“OA 流程提交办理接口”。

按钮权限和 API 权限可以独立配置，但 H5App 只有两者同时具备时才显示按钮，避免出现可见但调用必然失败的操作。

## 错误和兼容

- 撤回、评论、催办、表单修改和完成后修订权限保持不变。
- 旧 H5App 若仍调用统一任务完成接口，后端根据 action 使用新权限鉴权；迁移后的历史角色行为不变。
- 未执行迁移时，新版本后端会拒绝四类处理动作，不静默回退到旧总权限。
- 非法 action 返回参数错误，不显示为权限不足。
- 用户不再具有某动作权限时，已分配给他的任务仍存在，但只能执行其拥有权限的动作；任务归属和权限是两个独立条件。

## 验证

- 权限目录测试覆盖四个按钮权限、四个 API 权限和旧 handle 权限停用。
- 中间件测试覆盖 `approve`、`reject`、`return`、`submit` 的权限映射、无权限和非法 action。
- 路由目录测试确认统一完成接口不再绑定单一静态 handle 权限。
- 迁移测试覆盖八个权限、历史 allow/deny 授权复制和旧权限停用。
- H5App 结构检查覆盖四个按钮各自的按钮/API 双重权限判断。
- 后端聚焦测试、`go test ./...`、H5App `pnpm lint`、`pnpm type-check` 和 H5 构建按实际结果报告。
- 手工验证至少覆盖：仅通过、仅驳回、仅退回、仅提交办理、全部权限、无动作权限六类角色。

## 非目标

- 不拆分 `frontend/` 客户端的 `client:api:workflow:handle`。
- 不为四个动作新增四条业务 URL。
- 不改变驳回终止流程、退回上游节点、通过审批和提交办理的领域语义。
- 不修改绩效考评业务的提交、退回、撤回和归档权限。
